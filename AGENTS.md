# Commands
- `make help` lists every target; the Makefile is the entry point (`make fmt`, `make fmt-check`, `make test`, `make build-client`, `make e2e T=<file>`...)

# Commit Policy
- **Keep changes minimal**: One focused change per commit. Small commits are easier to review and revert
- **Sign-off**: every commit needs a `Signed-off-by: Name <email>` line (the DCO, `git commit -s`; `make check-dco BASE=<revision>`); an AI assistant's `Co-Authored-By` line does not replace it
- **Licensing**: every source file starts with `SPDX-License-Identifier: Apache-2.0`, the documentation (`*.md`) as an HTML comment on its first line; a unit test of `src/testing.rs` fails without it. Do not copy code under a license that is not compatible with Apache-2.0 (GPL, LGPL); code of another origin keeps its notice and is listed in NOTICE
- **Must build**: Every commit must compile with `cargo build`
- **Must pass tests**: Run `make test` (the fast tier, `cargo test`) before committing. All tests must pass. `make test-all` (the slow tier: waiting tests, the P2P package, thin client, e2e scripts) before merging changes to the runtime, the monitor, storage, networking or the systemd integration
- **Tests**: integration tests are modules of `tests/integration/main.rs` (one binary, all tests in parallel in one process): no process-wide state (environment, cwd, signals: such a test runs its body in a child process, in the library with `testing::in_child` of src/testing.rs, which also holds the test that enforces the rule in src/ and tests/), no fixed sleeps or polling, wait for an event (a pidfd, a notification socket, a channel); a test that must wait long runs only with `VELARX_SLOW_TESTS=1`

# Rules
- Add inline comments only when strictly necessary.
- Do not add history about variables, symbols or functions to the code comments.
- It must be easy to debug issues that happen after a long time.
- Make knobs configurable in the .toml file.
- All the configuration knobs must end up in the config.toml.example file.
- Do not leave any warning or unused symbols, first check why they are not used and if really sure not needed, delete them.
- Do not add test generated data to git.
- Run `make fmt` and `make test` before committing. No warnings allowed.
- Add only necessary .md files to the repo.
- Never use polling.
- Backward compatibility with older velarx versions (stores, databases, wire formats, TOC and image formats, peers, config) is NOT a goal: change formats and protocols freely, no migration or compatibility code (a database has one schema version, which stays 1 for now: never raise `SCHEMA_VERSION` or the namespaces' `VERSION` again until a release starts versioning; a breaking schema change edits the schema in place, with no bump, and a store of an older build becomes unusable (it fails at the first statement that needs the new shape: delete it); a database of another version is refused; the lint of `src/testing.rs` fails on `migrate`, `legacy`, `backward compat` and `old format` in the sources, with a list of the lines that are interoperability with other tools). buildah and podman can be changed too (to use the fs-verity digest, for example) when that works better.
- Never look into the OCI runtime's private state directory.
- Never use "$OCI_RUNTIME run"; use "create" + "start".

# Binaries
- `velarx` is the engine and the command line (`velarx varlink` is the engine: it serves only varlink, the `org.velarx.*` interfaces). `velarx-client` is the thin client, built without the `engine` cargo feature (`make build-client`, i.e. `cargo build -p velarx-bin --no-default-features --bin velarx-client`: without `-p`, the other default members switch the engine features of their dependencies on): blocking code only (no tokio, no TLS, no database); keep engine code out of what it uses (what it shares with the engine lives in the packages `velarx-base` (ids), `velarx-registry` without its `engine` feature (credentials, certificates) and `velarx-wire` (requests, wire types, option and address syntax, the monitor's interface `org.velarx.Monitor` and its blocking client, cp)).
- The REST API for Docker and podman clients is implemented only in its own binary, `velarx-api` (`crates/api`), and the CRI only in `velarx-cri`: the `velarx` binary implements no Docker API, no podman REST routes and no HTTP server, and its dependencies carry none. Both frontends are clients of the typed varlink Engine interface. A behaviour that the command line and a compatibility API share (a wait condition, a filter, a state) is implemented ONCE, in a typed Engine method (`crates/core`, `src/engine_service.rs`) that the command line and the frontend both call; the frontend only maps the Docker or podman parameters, names and document shapes to it, so a rule never exists in two code paths and a fix lands in all of them.
- `velarx-monitor` the process that owns one container and looks after it (its log, its restart policy, its health checks; what happens to it is recorded and its network released by the monitor itself, from job threads that run `velarx_runtime::settle` (the database through `velarx_db::sync`, `velarx-netkernel`, `velarx-netdetach`; no tokio; the engine runs the same functions when no monitor is there), and a container has one lifecycle whether a command, the engine service or nothing else runs; `crates/runtime/src/monitor/settle.rs`) (std, rustix and serde_json only: keep it small, no tokio; it serves `org.velarx.Monitor`, `interfaces/org.velarx.Monitor.varlink`, from its poll loop, `crates/runtime/src/monitor/clients.rs`; the definition is made from the types of `crates/wire/src/monitor/iface.rs` by a test), `velarx-p2p` (the package `crates/p2p`, which depends on `velarx`, never the other way) is the only code that links libp2p, QUIC and the overlay network; the engine, the command line and the monitor know nothing of it (`src/testing.rs` fails on the word outside `crates/p2p`): it is a source named in `[[sources.external]]` (`org.velarx.Fetcher`), it reads the store through `org.velarx.Store`, and the overlay network is a network provider (`org.velarx.Network`, `[[network.providers]]`); its commands (`status`, `peers`, ...) are those of `velarx-p2p`, not of `velarx`; its settings are the `settings` table of its source in `config.toml` (`[[sources.external]]`, the one named by `--source`, default `p2p`; the engine keeps the table as it is and never reads it; `config.toml.example`), and its commands ask it on its control socket in plain text (`crates/p2p/src/control.rs`), not in varlink. `cargo build` and `cargo test` leave it out (`default-members`); `--workspace` or `-p velarx-p2p-bin` (the binary) and `-p velarx-p2p` (the library) build and test it (`make build-p2p`, `make test-p2p`).
- The binaries are packages of their own, `crates/bin` (`velarx-bin`: velarx, velarx-client) and `crates/runtime/bin` (`velarx-monitor-bin`: velarx-monitor) and `bin/` in the directory of each frontend (`velarx-api-bin`, `velarx-cri-bin`, `velarx-p2p-bin`): they hold the build script that reads the git state for `--version` and gives the link arguments (PIE with packed relocations), and hand the commit to the libraries at start (`velarx_base::buildinfo::set`). A build script that reruns dirties every target of its package, so no library may have one that reads the repository (or `VELARX_GIT_COMMIT`): every commit, checkout or rebase would recompile it and what depends on it. A library reads `velarx_base::buildinfo`, never `env!("VELARX_GIT_COMMIT")`. `-dirty` is decided when the script runs, which it does when HEAD, a source file or a manifest changes (not for documents). Tests that start a binary find it next to the test executable (`common::built_binary`); the tests of `velarx-bin` make `cargo test` build them.
- Release size: `opt-level = "z"` with 3 for the hashing and inflate crates, fat LTO. Keeping the binaries and the dependency count small is a goal, not a gated limit: measure `strip`ped sizes and `hyperfine -N velarx --version` (`make bench-startup`) before and after dependency changes and report the difference in the commit when a change is expected to move them. Regular expressions are `regex-lite`'s (the hook conditions and the name filters of the API are Go's: ASCII classes, no Unicode tables); do not add `regex`.
